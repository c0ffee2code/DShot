# Observer

The observer is the wingman's recording role: it only watches the ESC signal lines and changes nothing (the wingman's other role,
the ESC mock, is in `ESC_MOCK.md`; what the wingman is and how it is wired is in `README.md`). The code that runs on the wingman is
`board/observer.py`; the PC tools are in `tools/` and all start with `observer_`; the DShot scenario tests that drive the motors are in
`../dshot_protocol/`.

| Piece | File | Runs on |
|-------|------|---------|
| Recorder | `board/observer.py` | wingman |
| Start/end line (GPIO 15) | `main_pico/start_line.py` (the scenario runner drives it; `deploy.py` uploads it) | main Pico |
| Frame decoder | `tests/bench/dshot_frame_decode.py` (shared with the main Pico's own pin sampler, a different instrument) | PC and Pico |
| Run a recording (board handling in `wingman_board.py`) | `tools/wingman_run.py` | PC |
| Read the stream | `tools/observer_edge_log.py` | PC |
| Print / plot a recording | `tools/observer_analyze.py`, `tools/observer_stats.py` | PC |
| Wire record and the main Pico's record on one time axis (pacing, replies, decode stamps, lag, Core 1 behind-schedule events) | `scripts/session_timeline.py <session folder>` (`--from-ms/--to-ms` zoom, `--show` interactive window) | PC |
| AM32 expectations, per recording / side by side | `tools/observer_check_am32.py`, `tools/observer_am32_table.py` | PC |
| Per-start summary | `tools/observer_start_summary.py` | PC |

**One command for a recorded run:** `python scripts/run_session.py <scenario.json>` (a scenario is always recorded; a Pico-only device script is recorded only with `--observe`). The PC names the session from its clock, writes `session.json` (scenario, git commit and whether the tree was dirty, board IDs, command line), starts the observer, runs the scenario with that name (the main Pico uses it as its SD folder name, uploaded as `session_name.txt` by `deploy.py --session`), then pulls the SD session into the same folder. Verified Pico-only 2026-10-29 (ESC unpowered, so the run ended at the arming timeout as it should): the folder held `session.json run.log scenario.json capture.bin signal_observation.bin` (the Pico's `meta.txt` is folded into `session.json` since 2026-10-30). There is no Pico clock: `run_test.py` refuses to run without `--session`. Also run through it on 2026-10-29: a completed unidirectional run (armed after 2001 ms, observer valid=1, all of `session.json run.log scenario.json meta.txt capture.bin signal_observation.bin`), a device script, `run_scenarios.py` (two rounds) and the start-quality runner of that time (one run, ended at "did not arm"; removed since). The unidirectional scenario through `run_session.py` plus `observer_check_am32.py` on its `signal_observation.bin` is the smoke test of the whole chain now that the observer's own self-test is gone.

The observer is given a fixed budget of 150 s (+10 s on the PC side) from its start, counted over deploy and run; the longest scenario needs about 65 s (estimate), so a much longer scenario would need the budget derived from its `duration_ms`.

**The verdict.** The session verdict is made here, on the PC, and nowhere else (the main Pico reports facts only, decision/ADR-008). At the end of a run `scripts/session_summary.py` writes `summary.json` into the session folder and prints a per-line table (frames, share answered, replies with a real eRPM, "not running" replies and how many came after the line had run, replies starting within 10 us of our frame, AM32 check counts) with the reasons for a failed verdict. It reads the files in the folder (nothing else), takes each line's mode from the scenario, and can be re-run on any session folder written by the current runner. A line is flagged when it is commanded to spin and never reports a real eRPM, or reports "not running" for 50 frames or more after it had (the 50 is my choice, `LOST_SPIN_FRAMES`, not a measured figure). Device test scripts without a scenario get verdict "unknown".

Recordings go to `captures/<session>/signal_observation.bin`, next to the run's other files; the file is there only when the observer was
recording that run. Run by hand, `tools/wingman_run.py` names the folder by the current time, or `--session <name>` puts it in an existing run's folder. Not yet done: the RPM tests do not use sessions (and so get no summary) yet. The AM32 check needs each line's mode from the scenario: in the single-channel bidirectional scenario motor 1 is bidirectional and motors 2-4 are unidirectional, and reading those lines as bidirectional makes the check report "no complete frame" (it did on 2026-10-29; read with `--unidirectional` they pass). The tick limits in the check still assume an F051 build.

A second Pico 2 (unique ID `5d703f56522b50fd`; the main one is `31b4d922f5d5f436`; found by ID, never by COM number, and `tests/bench/wingman/tools/wingman_run.py` refuses any other board) records every edge of up to four lines and streams it to the PC over USB, with no SD card. Why: it shows what is on the ESC signal wires, our frames and the ESC's replies in one time base, which the main Pico can only see through its own decoder. `tests/bench/wingman/board/observer.py` runs on the observer (one PIO state machine per line counts 100ns ticks between edges, a DMA ring per line, Core 0 forwards; the end packet reports ring overruns and PIO receive stalls, and a record with either is invalid); `tests/bench/wingman/tools/observer_edge_log.py` (tested by `tests/pc/test_observer_edge_log.py`) turns the stream into frames and replies, `tests/bench/wingman/tools/wingman_run.py` runs a recording, `tests/bench/wingman/tools/observer_analyze.py` prints it (min / 1% / median / 99% / max / mean / std of the frame spacing, bit timing, frame length, reply delay and eRPM, the frames whose spacing is off the median, a timeline) and `--plot` draws the same as time series with every frame a dot (`--from-ms`/`--to-ms` zoom into a stretch; the numbers come from `tests/bench/wingman/tools/observer_stats.py`, tested by `tests/pc/test_observer_stats.py`). Wiring: the same GPIO number on both boards - the ESC signal lines GPIO 6-9 and the start/end line GPIO 15 (`tests/bench/wingman/main_pico/start_line.py`; the scenario runner drives it: low first thing, high from just before arming until the motors are stopped. The observer only starts its state machines after it has seen the line low for 2 ms, because the main Pico's undriven GPIO 15 drifts high within about 50 ms of a reset and would otherwise open the gate seconds early) - and a ground wire between the boards. The two-board check (main Pico sending 0 -> 60 -> 0 on GPIO 6-9 and 15, ESCs unpowered) passed on 2026-10-28 and again on 2026-10-29 after the folder cleanup (1,168 frames per line, frame spacing 1045.0us mean by the observer's own clock, all input-side AM32 checks pass); its stimulus program and `--check` were then removed (git `febda45` has them). `tests/bench/wingman/tools/observer_am32_table.py <bins>` lays several recordings side by side as one table per DSHOT speed (the envelope row above), and `tests/bench/wingman/tools/observer_check_am32.py <bin>` tests a recording against what AM32's firmware needs, derived from its pinned source (AM32's own bit threshold, the learned frame-length window, the DSHOT600 speed classification, the CRC polarity, the signal-loss limit, the arming gate; for bidirectional recordings also the 101-frame latch, reply coverage and silences, reply integrity and bit time, the arming silence); the input-side checks read our own frames; the reply-side ones were first run on recordings with an ESC attached on 2026-10-28 (their synthetic tests: `tests/pc/test_observer_check_am32.py`); F421 is the only MCU family supported (owner, 2026-11-05): the speed classification and the expected reply bit time are the F421 figures, the bench ESC's (`specification/KM55A2_DEFAULTS.md`); another ESC's family is read with `tools/esc_buddy/esc_buddy_run.py --read`, not guessed, and a reply bit time off the F421 figure is a warning. Results, 2026-10-28: no ESC (4 lines, 3 runs at DSHOT600, 2 at DSHOT300), every reading identical run to run - they are properties of the PIO waveform, and the observer resolves 0.1 us; figures in README's Operational Envelope, ESC-side figures on `specification/KM55A2_DEFAULTS.md`. Sustained USB rate measured 700 KB/s, four lines need about 400 KB/s. It sees logic levels only, not voltages.

**Can the recording be trusted?** Checked 2026-10-28/29 (two Picos, ESC unpowered, GPIO 6-9 and 15; the stimulus programs and check scripts used are in git at `febda45`; at that date the recording was `spy.bin` (current name `signal_observation.bin`), made by `spy.py` (current name `observer.py`) and read with `spy_edge_log.py` (current name `observer_edge_log.py`)). USB cannot delay a timestamp (the PIO counts the time itself); it can only lose data, so the checks are about loss:
1. **Every loss detector fires when made to.** Core 0 stalled 300 ms: `overruns=1 valid=0`. One line's DMA switched off: `rx_stall=1 valid=0` on that line. The PC stopped reading for 1 s: `overruns=1 valid=0` on all lines (USB back-pressure shows as an overrun, not as silent byte loss).
2. **Received bytes are reconciled.** `wingman_run.py` compares the bytes the PC received per line with the `bytes=` the end packet reports (`observer_edge_log.reconcile`) and marks a mismatch invalid; `observer_edge_log.parse_stream` warns on one. It has never fired on real data (unit-tested only); all 82 recordings made by 2026-10-29 reconcile.
3. **Known intervals read back to 0.21 us.** High and low times of 1 ms to 3.5 s, counted by a PIO program on the main Pico, were read back to within 0.21 us after one scale factor of -1.5 ppm (the two boards' crystals), across the 3.28 ms marker boundary, 1.02 s, 2 s and 3.5 s. An independent check: the least-squares period of 18,660 idle frames is 1044.998 us, -1.55 ppm. That test found two defects of the first version, both fixed: every 3.28 ms "quiet line" marker was counted 0.3 us short (65540 instructions, not 65534), so long intervals read 92 ppm low; and an edge within 0.1 us after a marker was lost (stream version `marker=v2` marks markers with the opposite level bit; `observer_edge_log` applies the corrected marker time to older recordings too, which can still lose an edge right after a marker). Neither touches results taken while frames flow: the line is never quiet for 3.28 ms then.
4. **Nothing lost under load.** 46.5 s, four bidirectional lines, throttle 0/60/250 cycles with Core 0 idle, printing over USB, writing SD and collecting garbage: the same 44,522 frames on each line (the period predicts 44,522.0), 0 bad CRC, 0 partial, no gap over 1.5 periods. The frame-spacing figures of that run are in BUG-011, where they belong.

# Spy

The spy is the wingman's recording role: it only watches the ESC signal lines and changes nothing (the wingman's other role,
the ESC mock, is in `ESC_MOCK.md`; what the wingman is and how it is wired is in `README.md`). The code that runs on the wingman is
`board/spy.py`; the PC tools are in `tools/` and all start with `spy_`; the DShot scenario tests that drive the motors are in
`../dshot_protocol/`.

| Piece | File | Runs on |
|-------|------|---------|
| Recorder | `board/spy.py` | wingman |
| Start/end line (GPIO 15) | `main_pico/start_line.py` (the scenario runner drives it; `deploy.py` uploads it) | main Pico |
| Frame decoder | `driver/dshot_frame_decode.py` (shared with the main Pico's own pin sampler, a different instrument) | PC and Pico |
| Run a recording (board handling in `wingman_board.py`) | `tools/wingman_run.py` | PC |
| Read the stream | `tools/spy_edge_log.py` | PC |
| Print / plot a recording | `tools/spy_analyze.py`, `tools/spy_stats.py` | PC |
| Wire record and the main Pico's record on one time axis (pacing, replies, decode stamps, lag, Core 1 behind-schedule events) | `scripts/session_timeline.py <session folder>` (`--from-ms/--to-ms` zoom, `--show` interactive window) | PC |
| AM32 expectations, per recording / side by side | `tools/spy_check_am32.py`, `tools/spy_am32_table.py` | PC |
| Per-start summary | `tools/spy_start_summary.py` | PC |

**One command for a recorded run:** `python scripts/run_session.py <scenario.json>` (the spy is on by default, `--no-spy` to skip). The PC names the session from its clock, writes `session.json` (scenario, git commit and whether the tree was dirty, board IDs, command line), starts the spy, runs the scenario with that name (the main Pico uses it as its SD folder name, uploaded as `session_name.txt` by `deploy.py --session`), then pulls the SD session into the same folder. Verified Pico-only 2026-10-29 (ESC unpowered, so the run ended at the arming timeout as it should): the folder held `session.json run.log scenario.json capture.bin spy.bin` (the Pico's `meta.txt` is folded into `session.json` since 2026-10-30); with `--no-spy` no `spy.bin`. There is no Pico clock: `run_test.py` refuses to run without `--session`. Also run through it on 2026-10-29: a completed unidirectional run (armed after 2001 ms, spy valid=1, all of `session.json run.log scenario.json meta.txt capture.bin spy.bin`), a device script, `run_scenarios.py` (two rounds) and `run_start_quality.py` (one run, ended at "did not arm"). The unidirectional scenario through `run_session.py` plus `spy_check_am32.py` on its `spy.bin` is the smoke test of the whole chain now that the spy's own self-test is gone.

The spy is given a fixed budget of 150 s (+10 s on the PC side) from its start, counted over deploy and run; the longest scenario needs about 65 s (estimate), so a much longer scenario would need the budget derived from its `duration_ms`.

**The verdict.** At the end of a run `scripts/session_summary.py` writes `summary.json` into the session folder and prints a per-line table (frames, share answered, replies with a real eRPM, "not running" replies and how many came after the line had run, replies starting within 10 us of our frame, AM32 check counts) with the reasons for a failed verdict. It reads the files in the folder (nothing else), takes each line's mode from the scenario, and can be re-run on any older session. A line is flagged when it is commanded to spin and never reports a real eRPM, or reports "not running" for 50 frames or more after it had (the 50 is my choice, `LOST_SPIN_FRAMES`, not a measured figure). Device test scripts without a scenario get verdict "unknown".

Recordings go to `captures/<session>/spy.bin`, next to the run's other files; the file is there only when the spy was
recording that run. Run by hand, `tools/wingman_run.py` names the folder by the current time, or `--session <name>` puts it in an existing run's folder. Not yet done: the RPM tests do not use sessions (and so get no summary) yet. The AM32 check needs each line's mode from the scenario: in the single-channel bidirectional scenario motor 1 is bidirectional and motors 2-4 are unidirectional, and reading those lines as bidirectional makes the check report "no complete frame" (it did on 2026-10-29; read with `--unidirectional` they pass). The tick limits in the check still assume an F051 build.

A second Pico 2 (unique ID `5d703f56522b50fd`; the main one is `31b4d922f5d5f436`; found by ID, never by COM number, and `tests/bench/wingman/tools/wingman_run.py` refuses any other board) records every edge of up to four lines and streams it to the PC over USB, with no SD card. Why: it shows what is on the ESC signal wires, our frames and the ESC's replies in one time base, which the main Pico can only see through its own decoder. `tests/bench/wingman/board/spy.py` runs on the spy (one PIO state machine per line counts 100ns ticks between edges, a DMA ring per line, Core 0 forwards; the end packet reports ring overruns and PIO receive stalls, and a record with either is invalid); `tests/bench/wingman/tools/spy_edge_log.py` (tested by `tests/pc/test_spy_edge_log.py`) turns the stream into frames and replies, `tests/bench/wingman/tools/wingman_run.py` runs a recording, `tests/bench/wingman/tools/spy_analyze.py` prints it (min / 1% / median / 99% / max / mean / std of the frame spacing, bit timing, frame length, reply delay and eRPM, the frames whose spacing is off the median, a timeline) and `--plot` draws the same as time series with every frame a dot (`--from-ms`/`--to-ms` zoom into a stretch; the numbers come from `tests/bench/wingman/tools/spy_stats.py`, tested by `tests/pc/test_spy_stats.py`). Wiring: the same GPIO number on both boards - the ESC signal lines GPIO 6-9 and the start/end line GPIO 15 (`tests/bench/wingman/main_pico/start_line.py`; `record_motor_start.py` and the scenario runner drive it: low first thing, high from just before arming until the motors are stopped. The spy only starts its state machines after it has seen the line low for 2 ms, because the main Pico's undriven GPIO 15 drifts high within about 50 ms of a reset and would otherwise open the gate seconds early) - and a ground wire between the boards. The two-board check (main Pico sending 0 -> 60 -> 0 on GPIO 6-9 and 15, ESCs unpowered) passed on 2026-10-28 and again on 2026-10-29 after the folder cleanup (1,168 frames per line, frame spacing 1045.0us mean by the spy's own clock, all input-side AM32 checks pass); its stimulus program and `--check` were then removed (git `febda45` has them). `tests/bench/wingman/tools/spy_am32_table.py <bins>` lays several recordings side by side as one table per DSHOT speed (the envelope row above), and `tests/bench/wingman/tools/spy_check_am32.py <bin>` tests a recording against what AM32's firmware needs, derived from its pinned source (AM32's own bit threshold, the learned frame-length window, the DSHOT600 speed classification, the CRC polarity, the signal-loss limit, the arming gate; for bidirectional recordings also the 101-frame latch, reply coverage and silences, reply integrity and bit time, the arming silence); the input-side checks read our own frames and are trustworthy now, the reply-side ones have only been run on synthetic recordings (`tests/pc/test_spy_check_am32.py`) until a recording with an ESC attached exists, and all tick-based numbers assume an F051 build. Sustained USB rate measured 700 KB/s, four lines need about 400 KB/s. It sees logic levels only, not voltages.

**Can the recording be trusted?** The evidence (loss detectors made to fire on purpose, known gaps read back to 0.21 us, 46.5 s with no lost frame, the two defects it found and fixed) is in `SPY_EVIDENCE.md`.

# Spy: is its data trustworthy?

The record of how the spy's timing and loss detection were checked (see `SPY.md` for what the spy is and how to use it).

## Checked 2026-10-28/29 (two Picos, ESC unpowered, GPIO 6-9 and 15)

The tools that produced these figures (stimulus programs `transmit_*_for_listener.py`, `check_listener_gaps/run/arm.py`, the spy self-test, `run_listened.py`) were removed in the 2026-10-29 cleanup; they are in git at commit `febda45`.

 USB cannot delay a timestamp (the PIO counts the time itself); it can only lose data, so the checks are about loss. (1) Each loss detector was made to fire on purpose and did: Core 0 stalled 300 ms -> `overruns=1 valid=0`; the DMA of one line switched off -> `rx_stall=1 valid=0` on that line; the PC stopped reading for 1 s -> `overruns=1 valid=0` on all lines (USB back-pressure shows as an overrun, not as silent byte loss). (2) `tests/bench/wingman/tools/wingman_run.py` (and `scripts/run_listened.py`, which uses it) now also compares the bytes the PC received per line with the `bytes=` the end packet reports (`spy_edge_log.reconcile`) and marks the record invalid on a mismatch; `spy_edge_log.parse_stream`, which every analysis script uses, prints a warning on a mismatch. This check has never fired on real data (unit-tested only). (3) Known intervals from a PIO program on the main Pico (`transmit_gaps_for_listener.py`: high and low times of 1 ms to 3.5 s, counted by the state machine itself) are read back by `scripts/check_listener_gaps.py` to within 0.21 us after one scale factor of -1.5 ppm (the two boards' crystals), across 1 ms, the 3.28 ms marker boundary, 6.55 ms, 100 ms, 500 ms, 1.02 s, 2 s and 3.5 s. **That test found two defects of the first version, both fixed:** every 3.28 ms "quiet line" marker was counted 0.3 us short (65540 instructions, not 65534), so a long interval read 92 ppm low (a 2 s hole 183 us short, the 1.02 s gate 93 us); and an edge landing within 0.1 us after a marker looked like another marker and was lost (stream version `marker=v2` now marks markers with the opposite level bit; `spy_edge_log` applies the corrected marker time to older recordings too, but those still can lose an edge right after a marker. Neither defect touches the start-problem findings: while frames flow, the line is never quiet for 3.28 ms, so no marker occurs; markers only exist in true silences before the first and after the last frame, and in the arming silence, where the bias was at most 27 us over 301 ms). An independent check of the 65540-instruction figure: the least-squares period of the 18,660 idle-stretch frames (no markers) is 1044.998 us, -1.55 ppm against the nominal 1045 us, which matches the -1.5 ppm the gap test found. All 82 recordings made so far reconcile (bytes received = bytes the spy reported). (4) 46.5 s, four bidirectional lines, throttle 0/60/250 cycles and Core 0 idle, USB printing, SD writing and gc (`transmit_modes_for_listener.py`, `scripts/check_listener_run.py`): the four lines carried the same 44,522 frames each (the period predicts 44,522.0 over the recorded time), 0 bad CRC, 0 partial, no gap over 1.5 periods, no lost data. Frame spacing by Core 0 activity (min / median / max us): idle 1024.6 / 1045.0 / 1069.0 (std 5.1), USB print 739.6 / 1044.0 / 1333.9 (std 42.8), SD write 856.3 / 1042.1 / 1286.9 (std 63.2), gc 978.7 / 1044.7 / 1095.4. The main Pico's own pin sampler (`test_core0_effect_on_pacing.py`, a different instrument on GPIO 10-13) read p1/p99/max: idle 1032/1058/1071, print 861/1232/1297, SD 867/1227/1310 us: the two instruments agree (BUG-011). (5) The arming start sequence on the Pico alone, 10 resets (`transmit_arm_for_listener.py`, `scripts/check_listener_arm.py`): the first frame 21.6 ms after the start line, 2,700-2,701 frames in 2.82 s, largest gap 1.18-1.57 ms, never a gap over 5 ms. The "one frame, then about 2 s of silence" seen twice with an ESC attached did not reproduce in these 10 resets; these used the pacing-probe start sequence (no reply gate, no SD session, no scenario loading), while the two cases came through the scenario runner's start path, so the scenario runner's start, Pico-only, is still to be tried. About "properly paced": with Core 0 idle the spacing stays within about +/-24 us of 1045 us; with USB printing or SD writing it swings by about +/-300 us (BUG-011). The pin-sampler comparison was a separate run, not simultaneous.

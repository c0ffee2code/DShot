# tests/ - what each folder checks and how the scripts work

Moved out of CLAUDE.md on 2026-10-31 (CLAUDE.md keeps one rule per folder; this page keeps the detail). Text is
verbatim as of the move.

**`tests/`** is split first by whether it needs hardware, then by what it checks. `tests/pc/` runs on a PC; everything under `tests/bench/` runs on the Pico with the bench attached. Each folder has one rule; a file that breaks its folder's rule goes elsewhere, not into a catch-all:

- **`tests/bench/dshot_protocol/`** - does the DShot link and the arming/telemetry behaviour hold on this ESC across motor counts and configurations (regular vs bidirectional, DSHOT300/600)? Belongs: the scenario runner and its JSON scenarios, plus the single-motor ESC probes (`test_bidir_restart_cycles.py`, `test_frame_arming_echo.py`, `test_frame_stalled_drain.py`). Does not belong: anything that measures physical RPM (the RPM-disk tests are removed until the disks return, backlog item W41), or code another group also needs (that goes to the `tests/bench/` root), or anything that does not need an ESC.
  Detail: `run_scenario.py` runs a scenario the way an application uses the library: it builds the motors (bidirectional ones use the frame receiver, the only one `BidirectionalDShot` has; since it fills its own PIO block, `scenario.py` rejects a scenario JSON that puts a unidirectional motor on the same block), wraps them in `MotorGroup`, runs `update()` on Core 1 through `core1_runner.py` (a Core 1 loop projects copy and adapt), and on Core 0 follows each motor's throttle profile and samples `raw_telemetry()`. Every Nth new capture (the scenario's `decode_every`) is decoded on the device (`decode_tally.py` tallies real replies, CRC failures and non-replies) and judged against the scenario's `expect` thresholds, so a run prints its own verdict. A motor with fewer than `decode_tally.MIN_SAMPLES` decodes is **not judged** on the decode thresholds (the verdict reads `pass (not judged: ...)`), never failed for it, so sampling less often cannot fail a run; the spin watch and the spy's recording judge the motor: `session_summary.py` judges the scenario's `min_crc_valid_pct` and `min_median_erpm` on every reply in `spy.bin` (a commanded bidirectional line; fewer than 20 replies is a note, not a failure), and lists anything not judged under `notes` in `summary.json` and the printed table. **Core 0 does no I/O per reply while the motors run** (owner's rule, 2026-10-31: I/O on the main Pico is the bare minimum while it controls motors; every wire edge is the spy's job): the poll counts passes in RAM, and the PicoBell Adalogger's SD card gets one sample record each time a capture is decoded (so every `decode_every`-th capture per motor, about 40 small writes a second at most; `bidir_capture_sink.py`, `capture_sink.py`, the ported `sdcard.py`; the PC names every session, the Pico has no clock): the time, the 4 throttles, each motor's latest raw capture (21-bit frame with its 9-bit publish token) and a flag byte naming the decoded motor and whether that decode failed. No decoded eRPM is stored (the PC decodes the raw words), and the scenario JSON is not copied to the card (`run_session.py` keeps it in the session folder). `meta.txt` says `capture_kind=sampled`; the analysis refuses a log without it. `scenario.py`/`throttle_profile.py` load and validate a scenario fail-fast before anything is armed, and `scenarios/*.json` is the scenario library (each file declares all 4 motors' wiring and a throttle profile per motor, plus a `hardware` block - name, `kv`, rotor `magnets`, and the `propeller` it carries (its name, or `none` for a bare shaft; required, since the propeller is the load a start has to catch against) - for every motor that is ever commanded to spin; `scenario.py` refuses to load one without it, and `bidir_capture_sink.py` copies it into the Pico's record of the run as `motorN_name/kv/magnets/propeller`; `run.log` prints it at the start, `summary.json` and the printed table name the propellers; the Pico writes that record as key=value lines in `meta.txt` on the SD card, and `scripts/pull_captures.py` folds it into the `device` section of the session's `session.json` and deletes the pulled `meta.txt`; every analysis script reads it through `scripts/session_files.py`, with no fallback to the old file: sessions up to 2026-10-30 were migrated once). The ESC reports electrical RPM, so a session's eRPM only becomes shaft RPM through that magnet count: shaft RPM = eRPM / (magnets / 2), and `analyze_bidir_capture_log.py` prints both. Run one with `scripts/run_session.py` on a scenario file; it requires `--load` (what the motors carry, `none` for bare shafts), written to `session.json` as `load` because nothing else in a session says it (`run_scenarios.py` takes the same option) (the PC names the session; it uploads via `scripts/deploy.py` inside `scripts/run_test.py`, runs, and pulls the SD session into `captures/<session>/` - see the spy paragraph below; `run_test.py` itself needs `--session`), or pull sessions left on the card with `scripts/pull_captures.py` (which deletes each pulled session from the SD card) and analyse it with `scripts/analyze_bidir_capture_log.py`, which decodes the logged samples with the independent PC decoder, checks the decode thresholds on them (the gap and rate thresholds come from the Pico's own counters in `meta.txt`) and cross-checks the device's tally and failed flags. `scripts/run_scenarios.py` runs one or more scenarios repeatedly (interleaved round by round when given several), classifying each attempt from `run_test.py`'s own printed output rather than a hand-rolled shell loop's string-matching - see its own docstring for why that distinction matters. It prints one `RUN` line per attempt and `RESULT`, `ARMING_TIME` and `SCHEDULE` summary lines, all `key=value` (`verdict=pass|fail|excluded`, `armed_ms=`, `margin_ms=`, min/median/max over the passes), so a long batch can be grepped. Every attempt is a full session (it calls `run_session()`): its own `captures/<session>/` folder with the spy's recording and a `summary.json`, named in the RUN line (`session=`, with `session_verdict=`), so a 20-run batch leaves 20 session folders.
- **`tests/pc/`** - PC-run unit tests of the pieces that need no hardware (belongs: anything that runs under plain Python with `fakes.py`; does not belong: anything that touches the Pico) (mailbox, decoder, command packet, `MotorGroup` against fake state machines, scenario loading): `python -m unittest discover -s tests/pc`. `fakes.py` stands in for `machine`, `rp2` and `utime`.
- **`tests/bench/pio_and_cores/`** - how the driver uses the RP2350's PIO blocks and its two cores. Needs the Pico only, no ESC or motor power: `test_capture_slot_stress.py` (two real cores), `test_stop_clears_queues.py` and `test_pio_lifecycle.py` (the first proves on real PIO that `stop()` leaves the send queue empty and that repeated start/stop does not exhaust the program store) and `test_pin_sampler.py`, `test_core0_effect_on_pacing.py`, `test_core0_io_options.py`, `test_core0_operation_cost.py` and `test_wire_frames.py` (a logic analyzer inside the Pico: a spare PIO state machine and DMA record the four transmit pins - `tests/bench/pin_sampler.py`, analysed by `pin_timing.py`, driven by `pacing_probe.py`, decoded at the wire by `dshot_frame_decode.py` - to measure the real frame spacing and bit timing of the paced loop on unused GPIO 10-13 with nothing attached, alone and while Core 0 prints over USB or writes to the SD card; BUG-011). Does not belong: anything that arms an ESC.

**The wingman (the second board).** A second Pico 2 (unique ID `5d703f56522b50fd`; the main one is `31b4d922f5d5f436`; found by ID, never by COM number) plays two roles. As the **spy** it records every edge of the ESC signal lines and streams it to the PC over USB, so our frames and the ESC's replies are seen on the wire in one time base. Its code is `tests/bench/wingman/board/spy.py`; the PC tools are `tests/bench/wingman/tools/spy_*.py`; wiring (same GPIO numbers on both boards: 6-9 signals, 15 start/end line, plus ground), tools, and the evidence that its timing can be trusted (gaps exact to 0.21us, loss detectors proven, 46.5s with no lost frame) are in `tests/bench/wingman/SPY.md`. The wingman reads the main Pico's wiring and settings (pins, which lines are bidirectional, DSHOT speed, run length) from the scenario or start config being run, never from constants of its own (`tests/bench/wingman/tools/wingman_plan.py`). `python scripts/run_session.py <scenario.json>` runs a scenario as one session (the PC names it, `session.json` records what was run, the spy is on by default, `--no-spy` skips it, the SD session is pulled into the same folder, and `summary.json` is computed from the files in it by `scripts/session_summary.py`: the scenario's outcome copied from the Pico, per-line facts and AM32 check verdicts computed from `spy.bin` with each line's mode taken from the scenario, and a pass/fail verdict with its reasons; re-run it on any session folder). By hand: `python tests/bench/wingman/tools/wingman_run.py [--session <name>]` saves `captures/<session>/spy.bin` (present only when the spy recorded that run). **ESC mock:** with the ESC disconnected, `--esc-mock` (on `run_session.py` or `wingman_run.py`) makes the wingman also answer the main Pico's frames with recorded real ESC replies (`tests/bench/wingman/`), so the whole reply path and Core 0's decoding run with no ESC and no motor; the session is marked `esc_mock` in `session.json` and its summary and is not evidence about an ESC. Any tool that counts or compares sessions (arming rate, start quality, statistics over a folder) must skip a session for which `session_files.is_evidence(folder)` is False. Short version of the pacing result: with Core 0 idle the frame spacing stays within about +/-24us of 1045us; with USB printing or SD writing it swings by about +/-300us (BUG-011).

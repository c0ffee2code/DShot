# tests/ - what each folder checks and how the scripts work

Moved out of CLAUDE.md on 2026-10-31 (CLAUDE.md keeps one rule per folder; this page keeps the detail). Text is
verbatim as of the move.

**`tests/`** is split first by whether it needs hardware, then by what it checks. `tests/pc/` runs on a PC; everything under `tests/bench/` runs on the Pico with the bench attached. Each folder has one rule; a file that breaks its folder's rule goes elsewhere, not into a catch-all:

- **`tests/bench/dshot_protocol/`** - does the DShot link and the arming/telemetry behaviour hold on this ESC across motor counts and configurations (regular vs bidirectional, DSHOT300/600)? Belongs: the scenario runner and its JSON scenarios, plus the single-motor ESC probes (`test_bidir_restart_cycles.py`, `test_frame_arming_echo.py`, `test_frame_stalled_drain.py`). Does not belong: anything that measures physical RPM (the RPM-disk tests are removed until the disks return, backlog item W41), or code another group also needs (that goes to the `tests/bench/` root), or anything that does not need an ESC.
  Detail: `run_scenario.py` runs a scenario the way an application uses the library: it builds the motors (bidirectional ones use the frame receiver, the only one `BidirectionalDShot` has; since it fills its own PIO block, `scenario.py` rejects a scenario JSON that puts a unidirectional motor on the same block), wraps them in `MotorGroup`, runs `update()` on Core 1 through `core1_runner.py` (a Core 1 loop projects copy and adapt), and on Core 0 follows each motor's throttle profile and samples `raw_telemetry()`. Every Nth new capture (the scenario's `decode_every`) is decoded on the device (`decode_tally.py` tallies real replies, CRC failures and non-replies); the tallies are facts, printed and written to the Pico's record, and feed the spin watch. **The main Pico reports facts and never judges a run** (ADR-008): it may bail out early (arming timeout, Core 1 error, `max_gap_ms` or `min_record_rate_hz` missed - both measure its own polling, not the ESC -, the spin watch, the over-speed guard, Ctrl-C, a Core 1 loop that did not stop), and then reports the outcome `aborted: <reason>` and exits non-zero; a reason of its own states the measured value against its limit (`motor 0 throttle=215: no real eRPM for 2004ms > limit=2000ms`) and draws no conclusion, and a Core 1 error keeps its exception type; a run that reached its end reports `completed` and exits zero. Its console ends with `=== Run completed ===` or `=== Run aborted ===`, never pass or fail. The session verdict is `session_summary.py`'s alone: it judges the scenario's `min_crc_valid_pct` and `min_median_erpm` per line on the replies in `spy.bin` from the throttle step onward (the first of three equal frames of 48 or more; a commanded bidirectional line; fewer than 20 replies is a note, not a failure), reports the replies before the step (the arming phase: count, bad CRC, early starts) as facts and as a note when any had a bad CRC or started early, and lists anything not judged under `notes` in `summary.json` and the printed table. **Core 0 does no I/O per reply while the motors run** (owner's rule, 2026-10-31: I/O on the main Pico is the bare minimum while it controls motors; every wire edge is the spy's job): the poll counts passes in RAM, and the PicoBell Adalogger's SD card gets one sample record each time a capture is decoded (so every `decode_every`-th capture per motor, about 40 small writes a second at most; `bidir_capture_sink.py`, `capture_sink.py`, the ported `sdcard.py`; the PC names every session, the Pico has no clock): the time, the 4 throttles, each motor's latest raw capture (21-bit frame with its 9-bit publish token) and a flag byte naming the decoded motor and whether that decode failed. No decoded eRPM is stored (the PC decodes the raw words), and the scenario JSON is not copied to the card (`run_session.py` keeps it in the session folder). `meta.txt` says `capture_kind=sampled`; the analysis refuses a log without it. `scenario.py`/`throttle_profile.py` load and validate a scenario fail-fast before anything is armed, and `scenarios/*.json` is the scenario library (each file declares all 4 motors' wiring and a throttle profile per motor, plus a `hardware` block - name, `kv`, rotor `magnets`, and the `propeller` it carries (its name, or `none` for a bare shaft; required, since the propeller is the load a start has to catch against) - for every motor that is ever commanded to spin; `scenario.py` refuses to load one without it, and `bidir_capture_sink.py` copies it into the Pico's record of the run as `motorN_name/kv/magnets/propeller`; `run.log` prints it at the start, `summary.json` and the printed table name the propellers; the Pico writes that record as key=value lines in `meta.txt` on the SD card, and `scripts/pull_captures.py` folds it into the `device` section of the session's `session.json` and deletes the pulled `meta.txt`; every analysis script reads it through `scripts/session_files.py`, with no fallback to the old file: sessions up to 2026-10-30 were migrated once). The ESC reports electrical RPM, so a session's eRPM only becomes shaft RPM through that magnet count: shaft RPM = eRPM / (magnets / 2), and `analyze_bidir_capture_log.py` prints both. Run one with `scripts/run_session.py` on a scenario file; it requires `--load` (what the motors carry, `none` for bare shafts), written to `session.json` as `load` because nothing else in a session says it (`run_scenarios.py` takes the same option) (the PC names the session; it uploads via `scripts/deploy.py` inside `scripts/run_test.py`, runs, and pulls the SD session into `captures/<session>/` - see the spy paragraph below; `run_test.py` itself needs `--session`), or pull sessions left on the card with `scripts/pull_captures.py` (which deletes each pulled session from the SD card) and analyse it with `scripts/analyze_bidir_capture_log.py`, which decodes the logged samples with the independent PC decoder and checks that the device's tally and failed flags agree with it (it judges no threshold). `scripts/run_scenarios.py` runs one or more scenarios repeatedly (interleaved round by round when given several), classifying each attempt from `run_test.py`'s own printed output rather than a hand-rolled shell loop's string-matching - see its own docstring for why that distinction matters. It prints one `RUN` line per attempt and `RESULT`, `ARMING_TIME` and `SCHEDULE` summary lines, all `key=value` (`verdict=pass|fail|excluded`, `armed_ms=`, `margin_ms=`, min/median/max over the passes), so a long batch can be grepped. Every attempt is a full session (it calls `run_session()`): its own `captures/<session>/` folder with the spy's recording and a `summary.json`, named in the RUN line (`session=`, with `session_verdict=`), so a 20-run batch leaves 20 session folders. The `RUN` verdict and the `RESULT` totals are the arming outcome only; a closing `SESSION_VERDICTS runs= pass= fail= unknown= no_session=` line counts the session verdicts of the batch, so a batch of good arms cannot hide failed sessions.
- **`tests/pc/`** - PC-run unit tests of the pieces that need no hardware (belongs: anything that runs under plain Python with `fakes.py`; does not belong: anything that touches the Pico) (mailbox, decoder, command packet, `MotorGroup` against fake state machines, scenario loading): `python -m unittest discover -s tests/pc`. `fakes.py` stands in for `machine`, `rp2` and `utime`.
- **`tests/bench/pio_and_cores/`** - how the driver uses the RP2350's PIO blocks and its two cores. Needs the Pico only, no ESC or motor power: `test_capture_slot_stress.py` (two real cores), `test_stop_clears_queues.py` and `test_pio_lifecycle.py` (the first proves on real PIO that `stop()` leaves the send queue empty and that repeated start/stop does not exhaust the program store) and `test_pin_sampler.py`, `test_core0_effect_on_pacing.py`, `test_core0_io_options.py`, `test_core0_operation_cost.py` and `test_wire_frames.py` (a logic analyzer inside the Pico: a spare PIO state machine and DMA record the four transmit pins - `tests/bench/pin_sampler.py`, analysed by `pin_timing.py`, driven by `pacing_probe.py`, decoded at the wire by `dshot_frame_decode.py` - to measure the real frame spacing and bit timing of the paced loop on unused GPIO 10-13 with nothing attached, alone and while Core 0 prints over USB or writes to the SD card; BUG-011). Does not belong: anything that arms an ESC.

**The wingman (the second board).** A second Pico 2 (unique ID `5d703f56522b50fd`; the main one is `31b4d922f5d5f436`; found by ID, never by COM number) plays two roles. As the **spy** it records every edge of the ESC signal lines and streams it to the PC over USB, so our frames and the ESC's replies are seen on the wire in one time base. Its code is `tests/bench/wingman/board/spy.py`; the PC tools are `tests/bench/wingman/tools/spy_*.py`; wiring (same GPIO numbers on both boards: 6-9 signals, 15 start/end line, plus ground), tools, and the evidence that its timing can be trusted (gaps exact to 0.21us, loss detectors proven, 46.5s with no lost frame) are in `tests/bench/wingman/SPY.md`. The wingman reads the main Pico's wiring and settings (pins, which lines are bidirectional, DSHOT speed, run length) from the scenario or start config being run, never from constants of its own (`tests/bench/wingman/tools/wingman_plan.py`). `python scripts/run_session.py <scenario.json>` runs a scenario as one session (the PC names it, `session.json` records what was run, the spy is on by default - the wingman is a permanent part of the bench, and with it not connected the session stops before the main Pico runs anything -, `--no-spy` skips it and the session then has no verdict (`unknown`, with a note naming why), the SD session is pulled into the same folder, and `summary.json` is computed from the files in it by `scripts/session_summary.py`: the scenario's outcome copied from the Pico (`completed` or `aborted: <reason>`), per-line facts and AM32 check verdicts computed from `spy.bin` with each line's mode taken from the scenario, and a verdict built from required proofs, never from the absence of failures: the run finished cleanly (the Pico's outcome is `completed`; `aborted: <reason>` fails it with that reason), it armed within the published bound (`CLEAN_ARM_THRESHOLD_MS`, kept in `scripts/arming_bound.py`, shared with `run_scenarios.py`), the wire recording is valid and every motor pin of the scenario has complete frames of ours, our frames were correct (no failed AM32 check, no stray activity), every bidirectional motor commanded to spin reached a real eRPM, kept reporting it and kept answering and met the scenario's `min_crc_valid_pct` and `min_median_erpm` from the throttle step onward, and the last frames of every line carry throttle 0 (the stop was commanded). Each proof is `shown`, `failed`, `not shown` (could not be judged from the folder: a missing `spy.bin`, no arming time, too few replies for a threshold) or `not applicable`; the verdict is `fail` if any proof failed, `pass` only if every applicable proof is shown, and `unknown` otherwise, which is what a run without a valid wire recording gets even when the Pico reports it completed. `summary.json` carries the proof list (`proofs`) next to `verdict`, `reasons` (why it failed), `notes` (what was not shown) and `limitations`. **A unidirectional motor sends no reply, so that it spun cannot be shown from the wire**: it does not block a pass, and every such run lists it under `limitations` (visual confirmation by the operator is the only check until optical RPM measurement exists). A bidirectional motor held at throttle 0 for the whole run needs no spin proof; a session played with the ESC mock gets `not shown` for the arming and spin proofs, so its verdict is never `pass` (`unknown` when nothing failed, `fail` when something did: it is not evidence about an ESC); a device script run through `run_session.py` has no scenario outcome and is judged from the wire. The ESC reporting 'not running' after the stop is not required: on both 2026-11-10 sessions it still reports a decaying real eRPM in the last frame. Re-run it on any session folder). The exit code of `run_session.py` on the command line follows the verdict: 0 for `pass`, 1 for `fail` or when `run_test.py` returned non-zero, 2 for `unknown`; the function `run_session()` still returns `run_test.py`'s own code, which the batch runner uses). By hand: `python tests/bench/wingman/tools/wingman_run.py [--session <name>]` saves `captures/<session>/spy.bin` (present only when the spy recorded that run). **ESC mock:** with the ESC disconnected, `--esc-mock` (on `run_session.py` or `wingman_run.py`) makes the wingman also answer the main Pico's frames with recorded real ESC replies (`tests/bench/wingman/`), so the whole reply path and Core 0's decoding run with no ESC and no motor; the session is marked `esc_mock` in `session.json` and its summary and is not evidence about an ESC. Any tool that counts or compares sessions (arming rate, start quality, statistics over a folder) must skip a session for which `session_files.is_evidence(folder)` is False. Short version of the pacing result: with Core 0 idle the frame spacing stays within about +/-24us of 1045us; with USB printing or SD writing it swings by about +/-300us (BUG-011).

## Bench rules and mechanics

Moved out of CLAUDE.md on 2026-11-08 (CLAUDE.md keeps the rules, this page keeps the detail). Text is verbatim as of the move.

**One run is one session.** `scripts/run_session.py` (and the batch runner `scripts/run_scenarios.py`) names the session on the PC, records what was run in `session.json` (scenario, git commit, and the required `--load`: what the motors carry, `none` for bare shafts), has the **wingman** (a second board, found by ID, that records every wire edge; a permanent part of the bench) record the lines, pulls the Pico's SD record, and computes `summary.json`. **The main Pico reports facts, the PC judges (owner, 2026-11-11; ADR-008):** the main Pico reports what happened and may bail out of a run (outcome `aborted: <reason>`), and the session verdict is made only by `scripts/session_summary.py` from the wire recording; a run without that recording is `unknown`. Only the session format the current runner writes is read. **Owner's rule (2026-10-31): while the main Pico controls motors its I/O is the bare minimum (ESC I/O excepted); the spy records every wire edge.** A threshold that has too few replies on the wire to be judged is reported as not judged, never failed.

**Same mechanics as the scenario runner.** A bench test that runs motors uses the scenario runner's mechanics (`gc.collect()` before arming, `Core1Runner` at `group.UPDATE_INTERVAL_US`, the one paced loop, throttle set right after `ARMED`, Core 0 reading every reply every `poll_ms` and decoding every `decode_every`-th), so every result compares with the same baseline. A test that must differ (for example, no SD logging) says so in its header.

**Bench guards.** The scenario runner stops a run on two decoded-telemetry limits, both in `decode_tally.py`: `SpinWatch` (a motor commanded to spin that reports no real eRPM for 2 s) and `OverspeedWatch` (a motor that reports more than 300 eRPM per unit of its recently commanded throttle, 5 decodes in a row; throttle 60 reads about 8,400 eRPM, so its limit is 18,000). Both raise, so `fast_stop` zeroes the throttle. **The over-speed guard is switched off (owner, 2026-10-20)** by `OVERSPEED_GUARD_ENABLED = False` in `decode_tally.py` while the plateau reading on some channels is investigated; `run_scenario.py` prints "Over-speed guard: DISABLED" at the start of every run. Set it to `True` to bring it back; the no-spin limit and the throttle ceiling stay on. A guard only sees every `decode_every`-th reply, so a short disturbance can pass it: at one reply per 1045us period, 5 decodes 20 replies apart span about 100ms (arithmetic from the period, not measured).

**Shared test code and the Pico's flat file system.** Code shared by the bench test groups sits directly in `tests/bench/` (scenario loading, the decode tally, the Core 1 runner with `fast_stop`, the SD session recorder); it is not a test group and nothing in it has a verdict. Test groups may import this shared code and the wingman's `main_pico/start_line.py` (the start line the scenario runner drives), but never another group's files (a test that needs something from `dshot_protocol/` means that something belongs here instead). `deploy.py` flattens every file onto the Pico root and `run_test.py` finds a script by bare name, so keep file names unique across all of these folders.

**Scripts that touch hardware.** `scripts/deploy.py` only uploads the driver/harness files and resets the board - it runs nothing on the Pico. `scripts/run_test.py` is the one that spins motors (it requires `--session <name>`: the PC names every session, `scripts/run_session.py` makes the name and calls it, and the batch runners make one per attempt). `scripts/run_scenarios.py` wraps it for a batch of runs (`/run-scenarios`). All three are on this project's Claude Code permission allow-list (`.claude/settings.local.json`), since none is interactive and `run_test.py`/`run_scenarios.py` are the ones that touch hardware.

**Convention for bench code:** any script that spins motors ends its session with `fast_stop(group, runner)` from `tests/bench/core1_runner.py` (throttle 0 while the loop runs, then stop the loop, then `disarm()`), and treats a `False` result as a failed run. Scripts driving a single motor without `MotorGroup` send their own zero frames before `stop()` (see `tests/bench/dshot_protocol/test_frame_arming_echo.py`); scripts that never command a throttle (`tests/bench/pio_and_cores/test_pio_lifecycle.py`) need neither.

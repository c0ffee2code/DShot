# AM32 Firmware Knowledge

What AM32's firmware does, as the bench ESCs run it: **AM32 2.22** on the **F421** MCU (target
`SKYSTARS_KM55_V2_F421`, `KM55A2_DEFAULTS.md`), settings layout 4. Every claim is checked against AM32's source at
the 2.22 release; where a generic protocol description and AM32's behavior disagree, this page describes AM32's
behavior (see `DSHOT.md` for the protocol as generically defined). Where the code differs per MCU family, the F421
code is quoted.

**Sources (permalinks):**
- [`am32-firmware/AM32` @ `v2.22` (`3863f9df`)][am32]
- [`am32-firmware/AM32-bootloader` @ `578ff29c`][bl] - section 1 only. The bench ESCs carry an older bootloader
  (version 1, `KM55A2_DEFAULTS.md`) whose source revision is not known; section 1 is not confirmed against it.

## 1. Bootloader

Every reboot runs the bootloader first. `checkForSignal()` decides whether to jump straight to the
application or wait for a firmware update over the signal line:

1. Samples the signal line with a pull-down, up to 4,000 reads 10us apart; jumps to the application
   if more than 450 of those reads were low.
2. If not, switches to a pull-up and samples again (500 reads); if the line was *never* low across
   those reads, it stays parked in the bootloader (a permanently-high line cannot escape this way).
3. If not, floats the pin and samples once more; any low reading at all jumps to the application.

```c
#define low_pin_count_threshold 450
#define pull_down_pin_count_interations 4000
```
[`bootloader/main.c#L1095-L1158`][bl-checkforsignal]

Once in the bootloader's serial command loop, it only exits back to the application if the line
stays low for 20ms, or after more than 100 invalid/failed reads - each failed read increments the
same counter the loop checks:
[`bootloader/main.c#L840-L854`][bl-serialread] (20ms-low path),
[`#L1042-L1046`][bl-receivebuffer] (invalid-read counter), [`#L1275-L1280`][bl-mainloop] (loop exit)

## 2. Startup

After the bootloader hands off, `playStartupTune()` runs with interrupts disabled
(`__disable_irq()`/`__enable_irq()`), *before* input capture is enabled - any frames arriving
during it are not seen at all. The default tune is three 200ms beeps, 600ms total; a custom tune
can take longer.
[`Src/sounds.c#L118-L146`][sounds-startup], confirmed ordered before input capture arms at
[`Src/main.c#L2038-L2055`][main-startup]

## 3. Input capture and speed detection

AM32 captures a command frame's 32 edges with timer input capture + DMA, then decides each bit from
the whole frame's measured length rather than sampling at fixed points: a pulse is a "1" once it
exceeds 1/32 of the frame's own first-to-last-edge span (about 48% of a bit).
```c
dshot_frametime = dma_buffer[31] - dma_buffer[0];
halfpulsetime = dshot_frametime >> 5;
dpulse[i] = (pdiff > halfpulsetime);
```
[`Src/dshot.c#L72-L83`][dshot-frame]

Until a speed is detected, every captured frame is classified into one of two speed bands from
the intervals between its edges 0 to 30: the shortest interval, and their sum divided by 32
([`Src/signal.c#L239-L253`][signal-detectinput]):
```c
if ((smallestnumber >= 1) && (smallestnumber < 4) && (average_signal_pulse < 60)) {   // DSHOT600 (and 1200)
    ic_timer_prescaler = 0;
    buffer_padding = 14;
    inputSet = 1;
}
if ((smallestnumber >= 4) && (smallestnumber <= 8) && (average_signal_pulse < 100)) {  // DSHOT300
    ic_timer_prescaler = 1;
    buffer_padding = 7;
    inputSet = 1;
}
```
[`Src/signal.c#L201-L228`][signal-checkdshot] (abridged). A frame that matches neither band sets nothing, and the
next frame is classified again; once a band matched, `inputSet` stays 1 and the choice is final. AM32 only
documents support for DShot300 and DShot600 (its own README, "Dshot(300, 600) motor protocol support", and
wiki.am32.ca, "Compatible with PWM and BiDirectional DShot300/600 protocols") - DShot150 and DShot1200 are not
listed as supported, even though the band logic above has no distinct DShot1200 path of its own: a DShot1200
signal's timing happens to fall inside the DShot600 band's thresholds, which is incidental behavior from the band
math, not a documented or intentionally supported mode.

On the bench ESC's F421 (120MHz) the classification runs at a fixed capture clock of 120MHz / 21 = 5.714MHz, a
0.175us tick (`ic_timer_prescaler = CPU_FREQUENCY_MHZ / 6`, [`Mcu/f421/Src/IO.c#L16`][io-f421-icpsc]; the timer
divides by the register value + 1). The `average_signal_pulse < 60` bound is then a span of edges 0 to 30 under
about 336us. The counts are whole ticks, so a pulse is counted as the tick count just below or just above its
length, depending on where it starts against the clock. A DShot 0-bit's high (3/8 of a bit, `DSHOT.md`) is 0.625us
at DSHOT600, 3.57 ticks, counted as 3 or 4 (band: under 4), and 1.25us at DSHOT300, 7.14 ticks, counted as 7 or 8
(band: 4 to 8). A frame classifies as DSHOT600 only if at least one of its pulses is counted as 3 or less: a frame
whose shortest pulses are all 0-bit highs (an all-zero word, such as unidirectional throttle 0 with its plain CRC)
counted as 4 matches the DSHOT300 band instead.

Once a speed is detected, every later frame is checked against the per-band acceptance window described next,
which runs on a different capture clock.

## 4. The frame-length acceptance window

Once a speed is detected, every later frame still has to pass a length check before anything else
happens (signal-loss timer reset, CRC, everything) - the window starts wide open (0 to 50,000
capture-clock ticks), then AM32 averages 8 zero-throttle frames while disarmed and tightens it to
±1/16 of that average:
```c
if (dshot && (average_count < 8) && (zero_input_count > 5)) {
    average_count++;
    average_packet_length += (dma_buffer[31] - dma_buffer[0]);
    if (average_count == 8) {
        dshot_frametime_high = (average_packet_length >> 3) + (average_packet_length >> 7);
        dshot_frametime_low  = (average_packet_length >> 3) - (average_packet_length >> 7);
    }
}
```
[`Src/signal.c#L31-L32`][signal-frametime] (initial values), [`#L166-L174`][signal-average]
(averaging/tightening). After classification the capture clock is 120MHz at DSHOT600 (`ic_timer_prescaler = 0`)
and 60MHz at DSHOT300 (`1`) - not the classification pass's 0.175us tick (§3). The window is relative (±1/16 of the
learned average of edge 0 to edge 31), so the capture clock sets only its resolution: frames are judged by ±1/16 of
their own learned length, about 26.67us at DSHOT600 and 53.33us at DSHOT300 at the nominal bit rate (`DSHOT.md`).

## 5. Bidirectional-mode detection

AM32 detects bidirectional mode from the signal line's level, not from the CRC. After each captured
frame (while disarmed), it reads the pin; if high, a counter increments, and once that counter
exceeds 100 the mode latches:
```c
if (!armed) {
    if (dshot_telemetry == 0) {
        if (getInputPinState()) {
            high_pin_count++;
            if (high_pin_count > 100) { dshot_telemetry = 1; }
        }
    }
}
if (dshot_telemetry) { checkCRC = ~checkCRC + 16; }
```
[`Src/dshot.c#L87-L100`][dshot-detect]. Only once latched does AM32 expect the inverted command CRC
(see §12 for the reply-side CRC, which is unconditional). The latch never clears itself - once set,
bidirectional mode stays in effect until the next reboot.

**Why this doesn't block arming on a bidirectional host.** Before the latch, a bidirectional
host's zero-throttle frames carry an inverted command CRC that AM32's still-unlatched check
rejects - `newinput`/`dshotcommand` are only written inside the CRC-match branch (§7), so a
rejected frame leaves them untouched. Nothing on the boot-to-armed path actually needs that match:
- The frame-length check (not CRC) is what resets the signal-loss timer -
  `signaltimeout = 0` runs right after the length check, before CRC is even computed
  [`Src/dshot.c#L77`][dshot-siglentimeout], so a CRC-rejected frame still prevents a reboot as long
  as its length was valid.
- `newinput` and `adjusted_input` are each declared `= 0` [`Src/main.c#L553`][main-newinput-decl],
  [`#L459`][main-adjinput-decl], so a rejected frame simply leaves them at that boot default rather
  than at some other value - which already reads as "zero throttle" to everything downstream.
- `zero_input_count` increments whenever `adjusted_input == 0` and `calibration_required == 0`
  [`Src/signal.c#L175-L177`][signal-zeroinput]; `calibration_required` itself defaults to 0
  [`Src/signal.c#L20`][signal-calibrequired-decl]. True from boot regardless of whether any frame's
  CRC has ever matched.
- `inputSet` (§16's own gate) comes from the separate speed-classification pass (§3), which
  doesn't check CRC either.
- The one counter that *does* depend on a CRC match, `dshot_goodcounts`
  [`Src/dshot.c#L106`][dshot-goodcounts], is incremented and never read anywhere else in the
  firmware - a diagnostic value, not a gate.

So bidirectional-mode detection (~101 frames, pin-level-based) and the arming gate (~1.02s,
counter-based) run on two independent timers from the same starting point, not one after the
other.

## 6. The telemetry-request bit

The 1-bit telemetry-request field in a command frame only triggers AM32's separate *serial* (UART)
telemetry path - it has no effect on whether a bidirectional GCR reply goes out, and no effect on
anything else:
```c
if (dpulse[11] == 1) { send_telemetry = 1; }
```
[`Src/dshot.c#L104-L109`][dshot-telembit], feeding `makeTelemPackage()`/`send_telem_DMA()` on the
UART at [`Src/main.c#L2260-L2271`][main-serialtelem]. The bidirectional reply itself is triggered
independently, by the capture event once bidirectional mode is latched (§8).

## 7. Commands

**Command-frame CRC**, checked the same way for every captured frame regardless of value: the
three-nibble XOR of the decoded 12-bit value, compared against the last 4 captured bits:
```c
uint8_t calcCRC = ((dpulse[0]^dpulse[4]^dpulse[8])<<3 | (dpulse[1]^dpulse[5]^dpulse[9])<<2
                  | (dpulse[2]^dpulse[6]^dpulse[10])<<1 | (dpulse[3]^dpulse[7]^dpulse[11]));
uint8_t checkCRC = (dpulse[12]<<3 | dpulse[13]<<2 | dpulse[14]<<1 | dpulse[15]);
int tocheck = (dpulse[0]<<10 | dpulse[1]<<9 | ... | dpulse[10]);   // the 11-bit value itself
```
[`Src/dshot.c#L84-L85`][dshot-crc] (CRC), [`#L102`][dshot-tocheck] (`tocheck`). Once bidirectional
mode is latched (§5), the inverted CRC is expected instead - the same `~checkCRC + 16` adjustment
shown there.

Throttle/command value handling on every captured frame:
```c
if (tocheck > 47) {
    if (EDT_ARMED) { newinput = tocheck; dshotcommand = 0; command_count = 0; return; }
}
if ((tocheck <= 47) && (tocheck > 0)) { newinput = 0; dshotcommand = tocheck; }
if (tocheck == 0) { newinput = 0; dshotcommand = 0; command_count = 0; }
```
[`Src/dshot.c#L129-L155`][dshot-input] - a value of 1-47 is stored as a pending command *and*
forces throttle to 0 for that frame; a value above 47 passes through as throttle (subject to an
`EDT_ARMED` input-type check, [`Src/main.c#L760-L786`][main-inputtype]).

With AM32's 3D mode (`eepromBuffer.bi_direction`) enabled, the throttle range instead splits into
two spin directions, roughly 48-1047 and 1048-2047:
```c
if (newinput > 1047) { adjusted_input = ((newinput - 1048) * 2 + 47) - reversing_dead_band; }
if (newinput <= 1047 && newinput > 47) { adjusted_input = ((newinput - 48) * 2 + 47) - reversing_dead_band; }
if (newinput < 48) { adjusted_input = 0; }
```
[`Src/main.c#L1231-L1305`][main-3d]

Commands only execute while armed and the motor is stopped. Beeps act on the very first frame;
every other implemented command needs 6 consecutive identical frames:
```c
if ((dshotcommand > 0) && (running == 0) && armed) {
    if (dshotcommand != last_command) { last_command = dshotcommand; command_count = 0; }
    if (dshotcommand <= 5) { command_count = 6; }   // beeps go immediately
    command_count++;
    if (command_count >= 6) { /* switch(dshotcommand) ... */ }
}
```
[`Src/dshot.c#L157-L166`][dshot-cmd]

What AM32 actually implements: 1-5 beep; 6 sends ESC info over the serial-telemetry UART
([`Src/main.c#L2267-L2271`][main-escinfo]); 7/8 set spin direction (persist with 12); 9/10 turn 3D
mode off/on; 12 saves settings to EEPROM; 13/14 enable/disable Extended DShot Telemetry (§10); 20/21
set spin direction for the current session only (not persisted); 36 is AM32's own programming
mode - the next two valid frames supply an EEPROM position and a value, and frame 37 commits them.
Everything else AM32 defines a code for (LED commands, audio/silent mode, the signal-line-telemetry
toggles, the generic telemetry-request codes 42-47) is received but ignored.
[`Src/dshot.c#L168-L230`][dshot-cmd-switch]

## 8. Telemetry reply generation

Once bidirectional mode is latched, AM32 sends a reply on *every* captured frame - armed or not,
and regardless of whether that frame's own CRC passed:
```c
if (dshot_telemetry) {
    if (out_put) { make_dshot_package(e_com_time); computeDshotDMA(); receiveDshotDma(); return; }
    else { sendDshotDma(); return; }
}
```
[`Src/signal.c#L138-L149`][signal-disarmed-bidir] (disarmed path). Armed, `transfercomplete()` starts the reply
with `sendDshotDma()` right after the capture and only sets a flag; the capture's decode (`computeDshotDMA()`) runs
afterwards in `processDshot()`, triggered through EXTI line 15, and once the reply is out the next reply is packaged
there the same way ([`Src/signal.c#L118-L131`][signal-armed-bidir],
[`Mcu/f421/Src/at32f421_it.c#L262-L269`][it-f421-exint], [`Src/main.c#L1744-L1760`][main-processdshot]).
Either way the send fires before that same capture's own CRC/command decode runs; the eRPM value it sends was
packaged one processing cycle earlier, not computed fresh from anything in the frame just captured. A consequence: a reply arriving proves only that a
frame was captured, nothing about whether that specific frame's command was accepted - CRC and
value checks (§7) run independently, after the reply for the *previous* capture has already gone
out.

## 9. eRPM encoding

The reply payload is the period of one electrical revolution, in microseconds, computed from six
commutation-interval samples (each in 0.5us units):
```c
e_com_time = ((commutation_intervals[0]+commutation_intervals[1]+commutation_intervals[2]
              +commutation_intervals[3]+commutation_intervals[4]+commutation_intervals[5])
              + 4) >> 1;   // COMMUTATION INTERVAL IS 0.5US INCREMENTS
```
[`Src/main.c#L2088`][main-ecom]. It's clamped to 65535
([`Src/main.c#L1751-L1755`][main-clamp]), and forced to 65535 outright when the motor isn't
`running` - this is AM32's fixed "not running" sentinel, sent whether the ESC is armed or
disarmed:
```c
if (!running) { com_time = 65535; }
```
[`Src/dshot.c#L284-L286`][dshot-notrunning]. The raw value then normalizes into a 3-bit exponent +
9-bit mantissa by a shift-search loop:
```c
for (int i = 15; i >= 9; i--) {
    if (com_time >> i == 1) { shift_amount = i + 1 - 9; break; } else { shift_amount = 0; }
}
dshot_full_number = ((shift_amount << 9) | (com_time >> shift_amount));
```
[`Src/dshot.c#L283-L301`][dshot-erpm]. A side effect of this construction: whenever the exponent
ends up non-zero, the mantissa's own top bit (bit 8) is necessarily set - relevant to telling an
eRPM frame apart from an EDT frame (§10).

**Reading it as shaft RPM.** `60_000_000 / period` is *electrical* RPM. AM32's telemetry path does
not use `motor_poles` (it appears in `main.c` only for the RPM-throttle limits, fixed-speed mode and
sine-mode startup), so the host divides by the motor's pole pairs, which is half its rotor magnet
count: `shaft_rpm = erpm / (magnets / 2)`. The six commutation steps are already inside the period.

**The eRPM payload right after a start, as plain code facts about `commutation_intervals[]`:**
- Declared zero-initialized at file scope: `uint16_t commutation_intervals[6] = {0};`
  [`Src/main.c#L432`][main-commint-decl].
- Written in exactly one place in the whole file, inside the per-commutation-step function, copying
  in a *different*, singular variable: `commutation_intervals[step - 1] = commutation_interval;`
  [`Src/main.c#L920`][main-commint-write].
- That singular `commutation_interval` variable is declared `volatile uint32_t commutation_interval
  = 12500;` [`Src/main.c#L570`][main-cominterval-decl] - not 0.
- `old_routine`, a separate flag, is declared `= 1` [`Src/main.c#L458`][main-oldroutine-decl] and
  is only ever cleared to 0 from inside the function that handles a detected zero-crossing in
  AM32's polling-mode startup routine - which itself only runs once the motor is already `running`.
- The motor-start sequence checks `if (running == 0) { ...; if (!old_routine) { startMotor(); }
  running = 1; ... }` [`Src/main.c#L1371-L1379`][main-runningflip] - `startMotor()` itself, if
  reached, calls the per-commutation-step function once, then sets `commutation_interval = 10000`,
  then sets `running = 1` [`Src/main.c#L1139-L1150`][main-startmotor].

## 10. Extended DShot Telemetry (EDT)

Commands 13/14 (§7) enable/disable an alternate reply mode that trades some eRPM frames for other
telemetry. Enabling sends one `0xE00` frame; disabling sends one `0xEFF`:
```c
if (send_EDT_init) { extended_frame_to_send = 0b111000000000; }   // 0xE00
if (send_EDT_deinit) { extended_frame_to_send = 0b111011111111; } // 0xEFF
```
In between, AM32 never sends two EDT frames back-to-back - a flag (`last_sent_extended`) forces a
normal eRPM reply on the pass immediately following any EDT frame, so eRPM replies always stay
interleaved. On eligible passes it cycles through: current, every 40th eligible reply
(`CURRENT_EDT_RATE_DIVISOR`), as `0x6nn` at 1A per LSB; voltage, every 200th
(`VOLTAGE_EDT_RATE_DIVISOR`), as `0x4nn` at 0.25V per LSB; temperature, every 200th
(`TEMP_EDT_RATE_DIVISOR`), as `0x2nn` at 1C per LSB.
[`Src/dshot.c#L242-L282`][dshot-edt] (framing/interleaving), [`#L40-L42`][dshot-edt-divisors]
(rate divisors)

**Telling an EDT frame from an eRPM frame.** This isn't a separate flag the receiver can check -
it falls out of the two encodings' shapes. An EDT frame's top nibble is always `0xE`/`0x6`/`0x4`/
`0x2` with bit 8 clear. A genuine eRPM frame's top bit (bit 8 of the 12-bit payload) is
necessarily set whenever its exponent is non-zero (§9's shift-search construction) - and `0xE00`/
`0xEFF`'s own top nibble, `0xE`, would require exponent 7, which forces bit 8 to 1 for a real eRPM
value. So a top nibble of `0xE` with bit 8 clear is structurally impossible as a genuine eRPM
reading, and unambiguously marks an EDT frame instead.

## 11. GCR encoding

AM32's 16-entry GCR symbol table:
```c
const char gcr_encode_table[16] = {
    0b11001, 0b11011, 0b10010, 0b10011, 0b11101, 0b10101, 0b10110, 0b10111,
    0b11010, 0b01001, 0b01010, 0b01011, 0b11110, 0b01101, 0b01110, 0b01111
};
```
[`Src/dshot.c#L20-L23`][dshot-gcr]. Line generation is NRZI-style: the marker is a driven-LOW
level (0), and each subsequent GCR "1" bit flips the line level from the one before it, while a
"0" keeps the same level:
```c
gcr[1 + buffer_padding] = 128;
for (int i = 19; i >= 0; i--) {
    gcr[...] = ((((gcrnumber & 1<<i)) >> i) ^ (gcr[previous] >> 7)) << 7;
}
gcr[buffer_padding] = 0;
```
[`Src/dshot.c#L338-L344`][dshot-levels] (the variant the F421 compiles; F051, F031, CH32V203 and NXP builds have
their own).

## 12. Reply CRC

Unconditionally inverted, on every reply, armed or disarmed - there is no separate "plain" reply
mode:
```c
for (int i = 0; i < 3; i++) { csum ^= csum_data; csum_data >>= 4; }
csum = ~csum;
csum &= 0xf;
```
[`Src/dshot.c#L303-L311`][dshot-csum]

## 13. Reply timing

The reply bit period comes from the same timer that captured the command, reprogrammed as a PWM
output with one timer period per bit: `(output_timer_prescaler + 1) * (pr + 1) / 120MHz` on the F421. `pr` is fixed
at 76 ([`Mcu/f421/Src/IO.c#L27-L28`][io-f421]); `output_timer_prescaler` is set by the speed classification (§3,
[`Src/signal.c#L201-L228`][signal-checkdshot]): 3 at DSHOT300 and 1 at DSHOT600 on CPU clocks above 100MHz, such as
the F421's 120MHz ([`Inc/targets.h#L6012-L6014`][targets-f421]).

| Speed | Prescaler | Divider | pr+1 | Reply bit period |
|---|---|---|---|---|
| DSHOT300 | 3 | 4 | 77 | 2.5667us |
| DSHOT600 | 1 | 2 | 77 | 1.2833us |

The ESC drives the reply line for `23 + buffer_padding` timer periods total (the DMA transfer
count), covering the idle-high padding, the marker, 20 data bits, and one trailing idle period:
```c
INPUT_DMA_CHANNEL->dtcnt = 23 + buffer_padding;
```
[`Mcu/f421/Src/IO.c#L62`][io-f421-dma] (`buffer_padding` is 7 at DSHOT300, 14 at DSHOT600, §3).

## 15. Signal-loss timeout

`signaltimeout` increments every main-loop pass and is cleared by any frame of valid/in-window
length - checked *before* that frame's CRC is known. If it ever exceeds half the loop frequency
while armed (500ms), or twice the loop frequency while disarmed (2 seconds), AM32 switches every
phase off and resets the MCU:
```c
if (signaltimeout > (LOOP_FREQUENCY_HZ >> 1)) {   // half second, armed
    if (armed) { allOff(); NVIC_SystemReset(); }
    if (signaltimeout > LOOP_FREQUENCY_HZ << 1) {  // 2 seconds, disarmed
        allOff(); NVIC_SystemReset();
    }
}
```
[`Src/main.c#L2137-L2163`][main-timeouts]. Until the timeout fires, the motor keeps its last
commanded throttle - there is no earlier ramp-down.

## 16. The arming gate

Arming runs inside a nominally-20kHz loop (`LOOP_FREQUENCY_HZ`, [`Inc/targets.h#L6181-L6183`][targets-loop]).
On the F421 the loop timer `TMR14` counts at 120MHz / (119 + 1) = 1MHz with `pr = 1,000,000 / LOOP_FREQUENCY_HZ = 50`,
so 51 counts per interrupt and a real rate of **19,607.84Hz**, not 20,000Hz
([`Mcu/f421/Src/peripherals.c#L169-L171`][per-f421-tmr14]). `tenKhzRoutine()` (the function containing the
arming-gate logic below) runs once per `TMR14` interrupt ([`Mcu/f421/Src/at32f421_it.c#L196-L199`][it-f421-tmr14]).

```c
if (!armed) {
    if (inputSet) {
        if (adjusted_input == 0) {
            armed_timeout_count++;
            if (armed_timeout_count > LOOP_FREQUENCY_HZ) {   // compared against the nominal 20000
                if (zero_input_count > 30) { armed = 1; /* ... arming tune ... */ }
                else { inputSet = 0; armed_timeout_count = 0; }
            }
        } else {
            armed_timeout_count = 0;
        }
    }
}
```
[`Src/main.c#L1519-L1567`][main-arming]. Because the counter increments at the real 19,607.84Hz
rate but is compared against the nominal constant 20,000, the gate actually takes
20,001 / 19,607.84Hz ≈ **1.02 seconds** of real time, not exactly 1.000s - a small, deterministic
consequence of the timer math. Any nonzero throttle resets the counter to 0 immediately, with no grace.

On arming, AM32 plays an arming tune (three rising tones, `playInputTune()`), repeated once per
detected battery cell if low-voltage cutoff is enabled.
[`Src/main.c#L1542-L1555`][main-armtune], [`Src/sounds.c#L219-L237`][sounds-input].
`playInputTune()` disables interrupts for its own duration the same way the startup tune does
(§2) - `__disable_irq()` at entry, `__enable_irq()` at exit, around three 100ms beeps
[`Src/sounds.c#L219-L237`][sounds-input] - so no telemetry reply can be sent or processed for that
~300ms (or longer with multiple cells), visible to a receiver as a reply gap.

**Time to armed, cumulative.** Not a separately-verified figure - a sum of facts already cited
above in this page, assuming the host begins sending valid DShot frames (eventually settling at
zero throttle) as soon as each starting state allows it. The arming gate's own counter
(`armed_timeout_count`, ~1.02s) counts real elapsed time via a hardware timer tick, not frames,
but it only starts once `inputSet` is set - so §3's speed-classification pass (a handful of
frames) is a serial prerequisite, not something that overlaps the 1.02s. The other precondition,
`zero_input_count > 30`, is not serial: it's a frame-arrival count that keeps incrementing
throughout the same 1.02s window at whatever rate the host happens to be sending, and reaches 30
well before the timer does at any practical send rate - so it adds nothing on top:

| Starting point | What adds up | Approx. total |
|---|---|---|
| Already running firmware, past its startup tune, host starts a zero-throttle stream now | `inputSet` from speed classification (§3, a handful of frames) + arming gate (§16 above, ~1.02s) | **~1.05s** |
| Power-on, with host frames already present | Bootloader escape (§1, bounded by its own 4,000×10us pass - up to ~40ms) + startup tune (§2, 600ms, interrupts disabled - no frames are seen during it) + the row above | **~1.7s** |
| Power-on, bootloader parked instead (line held high with no frames) | Escape time - driven by how the host holds the signal line, not a fixed duration (§1) - plus the row above's tune and gate (~1.65s) | **escape time + ~1.65s** |
| Rebooting mid-session (signal-loss timeout, §15 - the only cause on this page that calls `NVIC_SystemReset()`; stuck-rotor protection, §18, stops the motor but does not reboot) | Same as the power-on-with-frames-present row above | **~1.7s after the reset itself completes** |

Bidirectional-mode detection (§5) runs on its own, pin-level-based counter that doesn't gate or
wait on any of the above (see §5's "why this doesn't block arming" note) - it typically finishes
well before the arming gate does, but isn't on this table's critical path either way.

The throttle threshold to actually start the motor is normally `input >= 47`; with AM32's
sine-start mode enabled (`eepromBuffer.use_sine_start`), it's `input >= 127` instead:

```c
if (input >= 47 + (80 * eepromBuffer.use_sine_start)) {
```

## 18. Stuck-rotor / back-EMF timeout protection

While `running`, a hardware interval timer counting in 0.5us ticks is checked against 45,000
(22.5ms); past that with no back-EMF zero-crossing, a timeout counter increments:
```c
if (INTERVAL_TIMER_COUNT > 45000) { if (running) { bemf_timeout_happened++; } }
```
[`Src/main.c#L2430-L2445`][main-stuck-count] (the F421's interval timer `TMR6` counts at 120MHz / (59 + 1) = 2MHz,
a 0.5us tick, [`Mcu/f421/Src/peripherals.c#L162-L164`][per-f421-tmr6]). The failure limit is 100 timeouts
if the adjusted throttle is below 300, or 10 timeouts at/above 300:
```c
if (adjusted_input < 300) { bemf_timeout = 100; } else { bemf_timeout = 10; }
```
[`Src/main.c#L2209-L2213`][main-stuck-limit] (the `else` of a `crawler_mode` branch; `crawler_mode` is
declared `char crawler_mode = 0; // no longer used //`, [`L377`][main-crawler], so the 300 test always applies).
Past the limit, AM32 cuts all phases and forces throttle to 0:
```c
if ((bemf_timeout_happened > bemf_timeout) && eepromBuffer.stuck_rotor_protection) {
    allOff(); maskPhaseInterrupts(); input = 0; bemf_timeout_happened = 102;
}
```
[`Src/main.c#L1310-L1314`][main-stuck]. The comparison is `>`, so the cut comes when the counter *exceeds*
the limit: after **101** intervals of 22.5ms (2.27s) below adjusted throttle 300 and after **11** (0.25s) at
300 or above, each counted from the last zero-crossing. The counter clears under any of: more than 1,000
zero-crossings seen, throttle returning to 0, more than 100 zero-crossings with throttle still
below 200, or (with sine-start enabled) throttle below 160:
```c
if ((zero_crosses > 1000) || (adjusted_input == 0)) { bemf_timeout_happened = 0; }
if (zero_crosses > 100 && adjusted_input < 200) { bemf_timeout_happened = 0; }
if (eepromBuffer.use_sine_start && adjusted_input < 160) { bemf_timeout_happened = 0; }
```
[`Src/main.c#L2194-L2213`][main-stuck-clear]

**What "adjusted throttle" is.** With the ESC's `bi_direction` (3D mode) off, `adjusted_input` is the DShot
throttle value itself, with no offset:
```c
adjusted_input = newinput;                    // main.c, the non-bidirectional-motor branch
newinput = tocheck;                           // dshot.c: tocheck is the packet's 11-bit throttle field
```
[`Src/main.c#L1306-L1308`][main-adjusted], [`Src/dshot.c#L102`][dshot-tocheck] and
[`#L129-L131`][dshot-input]. So the 300 above is DShot 300 (throttle values start at 48, section 17).
With `bi_direction` on (3D mode, also forced on by `rc_car_reverse`,
[`Src/main.c#L1974-L1976`][main-rccar]) the value is remapped, `adjusted_input = ((newinput - 48) * 2 + 47) -
reversing_dead_band` for one direction and `((newinput - 1048) * 2 + 47) - ...` for the other
([`#L1284`][main-3d-map], [`#L1298`][main-3d-map-rev]), so the step between the two limits would sit at a
DShot value near 175 instead of 300.

**After a cut.** `input` is forced to 0 and the counter is set to 102, above either limit. With the throttle
still at 200 or above, the clearing rules that can apply are only `zero_crosses > 1000` and throttle 0, so, read
from the code, the motor stays cut until the host sends throttle 0. The ESC then replies the not-running word
(section 9).

## 19. Startup duty cycle

A minimum startup duty cycle, `min_startup_duty` (default 120, adjustable via
`eepromBuffer.startup_power`), floors the actual commanded duty during the startup ramp window
(while `zero_crosses` is still low), overriding whatever the linear input-to-duty map produced for
low throttle values; a separate ceiling, `startup_max_duty_cycle`, caps the other end:
```c
duty_cycle_setpoint = map(input, 47, 2047, minimum_duty_cycle, 2000);
// ... later, only during the startup window:
if (duty_cycle_setpoint < min_startup_duty) { duty_cycle_setpoint = min_startup_duty; }
if (duty_cycle_setpoint > startup_max_duty_cycle) { duty_cycle_setpoint = startup_max_duty_cycle; }
```
[`Src/main.c#L399`][main-minstartup] (declaration), [`#L1384`][main-dutymap] (linear map),
[`#L1491-L1498`][main-dutyclamp] (startup-window clamp).
